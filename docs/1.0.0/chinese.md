# Extended and user-oriented Versioning (扩展并面向用户的版本) 1.0.0

## 摘要
版本格式：主版本号.次版本号.修订号.微调号，递增规则如下：

1. 主版本号：当你做了不向下兼容或及其重大的修改，
2. 次版本号：当你做了功能性新增，
3. 修订号：当你做了问题修正，
4. 微调号：当你做了那些并不值得另开新修订号的微调修正（可选）。
如有必要，更多信息可以加到“主版本号.次版本号.修订号.微调号”的后面作为延伸。

## 简介
在软件分发的世界里，我们正面临着称作“版本号地狱”的混沌。

传统的[语义化版本](https://semver.org/)（SemVer）是为开发者设计的，它侧重于 API 的兼容性。然而，在通用应用、电子游戏、内容模组（或其他主要面向用户软件）中，可能根本没有所谓的“公共 API”，也就没有 API 兼容性这一说。

且，如果你仅仅因为修了一个错别字就更新 Patch 位，你会觉得版本号在虚假膨胀；但如果你不更新版本号，用户又会因为下载了同名但内容不同的文件而陷入冲突。

在这些领域，开发者往往陷入混乱：有人根据心情跳过版本号，有人把多次更新堆积在同一个版本里，导致用户无从判断更新的风险与价值。

作为这个问题的解决方案之一，我提议扩展并修改语义化版本标准，将版本号的侧重点改为用户体验的承诺。我称这套标准为“**扩展并面向用户的版本控制**”

## 扩展并面向用户的版本规范（ExuoVer）
本文档中的关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、 RECOMMENDED、MAY、OPTIONAL 按照 RFC 2119 中的描述进行解读。

1. 标准的版本号 MUST 采用 `X.Y.Z.A` 的格式，其中 X、Y、Z、A 均为非负整数，且 MUST NOT 在前方补零。X 是主版本号、Y 是次版本号、Z 是修订号、而 A 是微调号。每个元素 MUST 以数值递增。例如：`1.4.1.1` -> `1.4.1.2` -> `1.4.2`。

2. 版本发行后，MUST NOT 改变该版本的**任何**内容。任何修改都 MUST 以新版本发行。

3. 主版本号为 0 的软件处于开发初始阶段，一切都会随时改变，这样的软件 SHOULD NOT 被视为“完整的”或“稳定的”。

4. 1.0.0.0 的版本号 SHOULD 用于界定软件的第一个正式版本，代表软件基本功能已经完整或稳定，可以大规模发行。

5. Patch 修订号 Z（x.y.Z）MUST 在修复软件bug、数值调整、显著性能优化时递增。次版本号改变时，修订号 MUST 归零。

6. Minor 次版本号 Y（x.Y.z）MUST 在增加用户可感知的新功能、机制、内容，或对现有内容进行显著修改等时递增。主版本号改变时，次版本号 MUST 归零。

7. Major 主版本号 X（X.y.z）MUST 在软件产生以下改动时递增：
	- 导致数据完全不兼容的修改，
	- UI布局或交互逻辑彻底改变，
	- 改变底层引擎，
	- 软件核心定位改变，
	- 软件整个重新制作。

8. Tweak 微调号 A（x.y.z.A）SHOULD 在对软件做出并不值得递增修订号的修正，例如修正错别字与语法错误、视觉素材细微修改、修改用户通常不可见的内容时递增。主版本号、次版本号、修正号改变时，微调号 MUST 归零。如果微调号为 0，MAY 忽略不写。递增微调号的更新 MUST NOT 包含任何兼容性问题。

9. 如有必要，你 MAY 在一般的版本号末尾使用后缀，用于简单说明该版本的用途或该版本的开发阶段。例如“-rebuild”、“-alpha”、“-beta”等。后缀 MUST 只有全小写的 26 字母与数字，并在前面添加连字符。它们应该看起来像：`2.0.0-unity6`。

10. 版本号的比较遵循从左到右的优先级：：`1.0.0.0` < `1.0.1.0` < `1.1.0.0` < `2.0.0.0`

11. 版本号 MUST 具有唯一性，你 MUST NOT 通过只修改后缀来发布更新，每个版本号也 MUST 只存在一个后缀，如果需要修改任何东西，请修改版本号。
